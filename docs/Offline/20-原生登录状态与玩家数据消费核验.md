# `Native_SDKLoginEnd` 对状态与玩家数据的实际消费

## 已获证据与待证事项

Java 声明和静态调用站点来自 [Actions #42337879073](https://github.com/969981/PVZ2_Resources/actions/runs/42337879073)：`Native_SDKLoginEnd(long,int,String): void`，五个 Java 回调位置行 169、173、177、180、185。

[Actions #42338454193](https://github.com/969981/PVZ2_Resources/actions/runs/42338454193) 在同 SHA 的 ARM64 `libSrc.so` 中恢复了连续 `JNINativeMethod` 注册表候选（见 [[16-JNI注册表函数映射]]）；登录结束方法候选入口 RVA **`0x4A9B678`**。该地址仍需要 Ghidra 和真实 JNI 调用证据才能提升为动态验证。

## ARM64 JNI 形参与安全观察点

标准 JNI 调用通常将参数从 `x0=JNIEnv*`、`x1=jobject/jclass` 开始放入 AArch64 形参寄存器：

| 寄存器 | Java JNI 声明对应 | 待核实 |
| --- | --- | --- |
| `x2` | `long` 原生或引擎句柄 | 是否是本地游戏实例指针 |
| `w3/x3` | `int` 状态 | 具体分支/枚举/返回值与用户授权关系 |
| `x4` | `jstring` 对象引用 | Java 实参已确认来自 `loginResultBean.token`；Native 是否解码、存储或用于后续请求仍待验证 |

它们是 ABI 下的**形参位置推定**，不是已经核实的业务语义。原生代码可在函数入口把寄存器值复制至其他寄存器或栈槽，因此仅凭扫描 `w3/x4` 的出现次数也不能闭合全部数据流。

## 本轮新增静态分析

`scripts/offline/ghidra/PvZ2JniSemantics.java` 在原版 ARM64 `libSrc.so` 经 Ghidra 分析后的四个候选 JNI 函数上：

1. 校验候选 RVA 是否可映射到真实指令和函数入口；
2. 统计函数入口附近 160 条以内、最早直接读取 `x2/x3/x4` 的指令位置（只导出 RVA 和助记符）；
3. 对每个函数进行 Ghidra P-code 分析，只导出等于/不等于等比较指令关联的小整数常量及其地址；
4. 导出 `ghidra_jni_argument_uses.csv`，**不上传**反编译 C、原始汇编全集、游戏 ELF 或 APK；
5. 将已知实际 Java 分支的整数常量（`twpurchase_login_end_branch_shapes.csv` 及后续版本）与 Native 比较常量对账。

**验收限制**：即便 Ghidra 找到寄存器使用和比较常量，只能说明静态代码消费迹象；真正判断哪一条回调能建立本地单机玩家，仍必须在设备上证明入口实际执行、状态变更和原版游戏 UI 的变化。

## 最终接口接入准则

- 首先证明游戏引擎在获得何种有效**本地会话**后进入地图，不让它假定服务端已认证；
- 本地玩家标识独立于官方账号，不发送到联网接口；不模拟充值或在线账户权益；
- 使用真实关卡 ID、结算和存档格式接入 [[19-离线主菜单关卡结算重启读档验收规范]]；
- 当前仍没有经实测可进入主菜单、结算第一关并持久读档的离线 APK。

参见 [[18-离线单机里程碑与验收台账-2026-11-07]] · [[16-JNI注册表函数映射]]。

## 2026-11-07：Java 到 Native 实参来源已实测闭合

[Actions #42339491204](https://github.com/969981/PVZ2_Resources/actions/runs/42339491204) 真实同 SHA256 反编译分析发现五个 `Native_SDKLoginEnd` 调用使用：

- `x2` 对应 Java `long`：`TWPurchase.this.mNativeDriverPtr`（源码字段名）；
- `w3` 对应 Java `int`：行 169/173/177/180/185 分别传入 **0/1/1/1/0**；
- `x4` 对应 Java `String`：**`loginResultBean.token`**。

因此 **Java 实参来源已闭合**，但原生 `0x4A9B678` 函数如何处理 `w3`、是否通过 JNI 读取 `jstring`、是否将 token 用作联网认证、以及是否产生游戏玩家结构，仍属于必须从 ARM64 函数和运行时证明的事实，不能由参数名字反推。

为了避免全量 Ghidra 超时阻塞，另增加了 `scripts/offline/arm64_native_login_arg_probe.py` 与 `.github/workflows/pvz2-offline-native-jni-argument-probe.yml`，在四个同 ELF 的 JNI 入口对寄存器的最早直接读取做有界静态分析。**寄存器被读取并不等于已经确认状态/令牌的业务用途**。

原生结构已见 [[16-JNI注册表函数映射]]，验收总表见 [[18-离线单机里程碑与验收台账-2026-11-07]]。

# 原版被动对照与 Ghidra 原生分支实测（2026-11-08）

> [!warning] 真实结论
> 原版签名、飞行模式、只读 Frida 的实验推进到**拓维手机号登录界面**，而不是原版主菜单。签名重构分支的警告/退出路径和原版登录阻塞是两个独立问题；没有任何证据证明当前 APK 已可离线畅玩。

## 1. 可复核的 Android 原版被动对照

- [Actions #42443987206](https://github.com/969981/PVZ2_Resources/actions/runs/42443987206)，Artifact `pvz2-original-signed-local-jni-trial`（ID `13603291029`，mode=`passive-observer`）。
- 原版 CHN 4.2.8 APK SHA256 固定 `64b0f2cddb6221baf35fb32d4a0f6e64153428edf5ee5922beddb9726bedbda4`；本次未修改其签名。
- Android 11 x86_64 + ARM Native Bridge；飞行模式开启、隐私条款实际确认、Frida 成功通过 PID 6185 附加。
- `TRACE_HOOKS_INSTALLED=true`，原始日志的 `RESOURCE_LOADING_STAGE` 数值共 21 次，`current_stage` 实际出现 0、5，`time_hint` 观察值由 10 变为 6，未报告字段不可用。
- 5、120、420、600 秒检查时游戏进程均存活，均未观察到“盗版游戏”弹窗。
- **120 秒**截图仍显示 `正在解压文件1/6`。
- **420 秒和 600 秒**截图均显示拓维手机登录对话框，输入框为手机号、短信验证码，并可选择账号密码登录。两个 PNG 的字节 SHA256 均为 `cf913fb7d196169052b61bfdc4f08059805c46e34c7d7046442d79a12b0408f1`；只证明这两个采样画面相同，并非 UI 线程死锁证明。
- UI 背景仍有游戏加载文案；即使提示在后台出现，也不能把画面背景条长度当作真实资源加载进度或判断所有资源均已验证完成。
- 本次只读模式没有替换 `TWPurchase`、SDK 或 JNI 方法，不存在强制模拟 `Native_SDKLoginEnd` 的回调。这使其比先前的本地同步 JNI Hook 更适合用来确定**原始启动次序**。

**优先级纠正：**基于这次原版被动运行，不宜将问题统一概括为“卡 20%”。可见的当前阻挡是拓维登录 UI。之前部分替换登录回调的实验可能与之不同，需维持 A/B 隔离。

## 2. Ghidra 条件分支索引产物（不是补丁方案）

- [Actions #42444062793](https://github.com/969981/PVZ2_Resources/actions/runs/42444062793) 成功，Artifact `pvz2-arm64-surface-ghidra-callgraph`（ID `13603072953`）。
- 完整索引 `surface_branch_index.csv`：281 行 = 1 条入口记录、172 条直接调用、10 条间接调用、98 条条件分支。
- 覆盖两个 Ghidra 定义的函数：`FUN_057227F0`（145 行）及单层静态调用者 `FUN_0568D380`（136 行）。
- 静态结构：JNI 注册函数指针候选 `0x05722FF0` 落在 `FUN_057227F0` 内，当前不应将它视为未经验证的独立函数入口。
- 距该指针最近的静态条件分支包括 `0x05722FEC` (`cbnz`)、`0x05722FE4` (`tbnz`)、`0x05723000` (`tbz`)。
- **距离最近并不代表校验失败分支**。这些分支的输入、实际运行路径、签名数据依赖、到 `UI_ShowAlertDialog` / `Device_ExitApp` 的 CFG 控制依赖尚未验证。禁止按排序盲目打补丁。
- `surface_function_summary.json` 仍明确 `runtime_branch_verified=false`、`safe_offline_patch_verified=false`、`gameplay_verified=false`。

本轮在 PR #64 实验分支提交：

- `e715c6f3`：采集消息保留 `observation_source=static|instance`，且只在确有布尔字段时保留 `is_first_init`。

- 该修复是仪器可观测性改进，不会本身使游戏离线进入主菜单。旧版本只读实验已成功观测到静态字段数值；修复不能被宣传为解决了启动故障。

## 4. 下一项真实验收

1. **原版控制组：**持续保留“原版签名、无登录方法替换、飞行模式”的真实画面与资源阶段，分清 `Splash/解压` 与 `TwOfflineSDK` 初始化。
2. **本地玩家会话：**对 Java `TWPurchase` 异步协议和四个 JNI 入口 `Native_SDKInitStart/End`、`Native_SDKLoginStart/End` 做有来源的参数与状态转移分析。Java 已观察到 `Native_SDKLoginEnd(long,int,String)` 和 `loginResultBean.token`；原生如何消费这些值**仍未知**。不能把四次同步 JNI 调用替代真实 SDK 回调当作已成功登录。
3. **本地进度：**仅在原生引擎确认有效离线玩家会话后，定位关卡进度、奖励、存档读写路径，并与自行实现的 `LocalProfileStore` 比对；模块自身通过单测不能替代原版游戏存档。
4. **成功标准：**原版引擎主菜单可操作 → 飞行模式完成第一关及结算 → 强制停止 → 冷启动 → 本地进度正确恢复。每关真实截图/日志、APK SHA/运行模式齐全，缺任何一项仍标为 `offline_playable=false`。

## 5. 发布边界

可以开源自写 Ghidra/Frida 探针、脱敏报告、原创本地会话适配器、测试与用户自备合法 APK 的构建工具。不能因逆向分析就把原商业 APK、原始 `libSrc.so`、完整商业 Smali/素材自行重新授予开源许可。不要把原版签名私钥、在线账号数据或支付服务状态打包进公开发行物。

## 3. 为什么修复测试证据优先级

以往 `compare_startup_ab._warning()` 在读取到截图帧为 `false` 后就提前返回，可能忽略同一日志中的 `INTEGRITY_ALERT_REQUEST`。一次非警告画面截图不能否定更早一刻的 Frida 原生 UI 警告请求。本次修改：

1. `scripts/offline/compare_startup_ab.py`：先检查正向 Frida 事件，然后合并所有可用截图布尔观察，避免早期 `false` 掩盖后续 `true`。
2. `scripts/offline/consent_probe.py`：运行时分类同时消费经过限定类型的 Frida 警告事件和屏幕采样；`FAIL_INTEGRITY_WARNING` 优先于退出／ANR 的次级现象。
3. 新增针对遗漏警告截图、冲突观测、异常事件载荷的回归单测。
4. CI 失败消息输出真实 `status`；不再把所有失败写成“ANR or process exit”。

这只是改进真实证据与 CI 可读性，**没有绕过签名、交易校验或写入游戏权益**。

## 4. 下一技术关口

- 对照原始签名 APK 的 **passive-observer** 和重签版，保持同一 Android ABI、相同测试时点、尽可能相同的被动观测方法。旧原版 JNI 覆写实验与真正被动对照不能混为一谈。
- 若只有重签版触发警告，应继续审计实际签名／包信息读取时序，确定差异来自 APK 完整性、Native Bridge 还是其它资源／初始化条件，不能凭弹窗唯一推出原因。
- 获得可信的真实 ARM64 环境与 `libSrc.so` 运行时模块基址、PC/LR 之后，才能判断现有静态 JNI 入口候选 `0x05722FF0` 与实际分支的关系。x86_64 的 `LIBSRC_NOT_MAPPED` 不等于可验证的原生 RVA。
- 主菜单／第一关／冷启动存档仍须单独真实验收。不要将“CI 成功”或“进程存活”认作这些门槛通过。

## 5. 原版签名和重签 APK 已完成的 A/B

原版**被动观察** [Actions #42450836313](https://github.com/969981/PVZ2_Resources/actions/runs/42450836313)：
- 原版签名未改，`passive-observer` 无 SDK 回调替换。
- 同意隐私条款后 5/120/420/600 秒进程存活均为 `true`，正版警告采样均为 `false`。
- Frida 脚本加载成功，读取到 21 条资源字段样本，阶段枚举出现 `0`、`5`，**不能未经验证当作游戏进度百分比**。
- 原版没有进入主菜单，故只证明进程存活和资源阶段观测，并非可玩。

原版**生命周期观察** [Actions #42450836327](https://github.com/969981/PVZ2_Resources/actions/runs/42450836327)：
- Java SDK 探针安装 10 个重载，采到 16 个生命周期事件。
- 时序：`INITIALIZE_REQUEST` → `INIT_RUNNABLE` → `JNI_INIT_START` → `SDK_INIT` → `INIT_CALLBACK` → `JNI_INIT_END(status=0)` → `JNI_LOGIN_START` → `SDK_LOGIN`。
- 观测区间内**没有** `LOGIN_CALLBACK` 或 `JNI_LOGIN_END`，也未见登录成功的证据。原版仍卡在资源阶段/登录之后的未完成启动过程中。

重签版 [Actions #42459206236](https://github.com/969981/PVZ2_Resources/actions/runs/42459206236)：
- 5/25/45 秒存活为 `[true,false,false]`；`INTEGRITY_ALERT_REQUEST(exit_requested=true)` → `GAME_EXIT_REQUEST`，另有对话框堆栈。
- `activity_anr=0`、`java_fatal=0`、`native_signal=0`、`dns_failure=0`，本次不同于上一轮 ANR 结果。
- `native_trace.status=LIBSRC_NOT_MAPPED` 不等于游戏原生库一定未加载：x86_64 Native Bridge 的 ARM 客体映射可能并非 Frida 宿主模块列表中的可回溯 ELF。

**差异结论：** 重签和 SDK/JNI 改动都可能影响启动，本轮尚不能将所有差异唯一归因于“签名”。签名独立性要用原版 vs *仅重签不改 DEX* vs *改 DEX+重签* 在相同观察手段和检查点做三组对照；不能将 600 秒原版与 45 秒重签视为时间严格匹配的因果实验。

## 6. Native Bridge 与 ARM 客体调用栈的新诊断

本轮新增：
- Frida `TRACE_HOOKS_INSTALLED.native_module_probe`：仅报告宿主架构、模块数、`libSrc.so` 是否作为宿主模块映射、已识别的 Native Bridge 模块存在与否；
- 同一警告事件的 `native_trace.module_probe`：观察触发警告那一刻模块是否可寻址，区分 `OBSERVED`、`OBSERVED_FUZZY`、`LIBSRC_FRAMES_UNAVAILABLE`、`LIBSRC_NOT_MAPPED`；
- Android `ro.product.cpu.abi`、`ro.product.cpu.abilist`、`ro.dalvik.vm.native.bridge` 的脱敏值；
- Android `/proc/<PID>/maps` 只输出游戏客体 ELF 和翻译器文件映射是否存在及段数，不输出基址、全路径或内存内容；
- CI 分开计数准确回溯和 FUZZY 候选回溯，不再将 FUZZY 视为确定的原生 PC。

若真实运行显示 `libSrc.so` **有 /proc 文件映射但 Frida Process 找不到模块**，说明宿主模块枚举不足以观测对应 ARM 客体执行；尚不能凭 x86_64 的 `Thread.backtrace` 恢复原生 ARM PC。最强的后续核验是在实际 ARM64 Android 设备上以对应架构 Frida 只读观察模块基址和 PC/LR，并核实其相对 RVA，与 Ghidra 静态入口候选交叉验证。**当前未声称已取得真实 ARM64 原生调用栈。**

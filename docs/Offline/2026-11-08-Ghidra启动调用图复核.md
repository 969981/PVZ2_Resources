## 地址陷阱和下一步定位

`0x05722FF0` 是 ELF / Ghidra 注册指针候选，并非已被证明的目标函数**入口**；Ghidra 认为它落在 `0x057227F0` 所在函数中。若直接改写此 RVA，可能改到 JNI 注册处理或函数中段，破坏整个启动路径。

1. 在 Ghidra 中以 `FUN_057227f0` 和其调用者 `FUN_0568d380` 为起点，核验 JNI 注册表 `0x05FA9168` 的重定位及其真实目标（与 `0x05722FF0` 对应关系）；检查 `0x05722FF0` 是否落在指令边界，识别子函数或函数拆分错误。
2. 反查 `UI_ShowAlertDialog` 和 `Device_ExitApp` 的 JNI 函数/调用点，提取其共同上游调用者、分支条件、返回值和比较对象。**两个 API 的共享调用栈不等于已找到校验条件**。
3. 用 Frida **只读**拦截实际运行的已加载 `libSrc.so` 基址和候选函数入口，记录 thread id、LR、PC、回溯、调用先后、退出标志；区分正常初始化失败、签名校验失败、依赖不可用和其他路径。
4. 对“原版未重签名 APK”和“仅重签名、未应用离线补丁 APK”保持同设备/同系统环境的 A/B，对比初次偏离的原生分支，再将“本地用户初始化”作为独立变量测试。
5. 只在能够复现原生初始化并明确校验判断后，考虑最小局部实验；不以屏蔽 `killProcess` 或隐藏弹窗作为修复，因为仍可能卡死在主菜单前。

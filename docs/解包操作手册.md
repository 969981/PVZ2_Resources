# PVZ2 CHN 4.2.8 解包操作手册

返回 [[00-知识库首页]] · [[文件目录与职责]] · [[资源格式与文件用途]] · [[工作流与Artifacts]] · [[研究证据规范]]

> [!important] 适用范围
> 以下命令按**仓库现有脚本真实参数**编写。Stage 1、RSGP 组导出、CN Resource_Tool 内部文件与 RTON→JSON 已在相同 CHN 4.2.8 APK 的 GitHub Actions 中验证；这不等于每台 Windows 本地环境已经运行成功。本文主要记录 Stage 0～3 的真实参数；媒体转换、关卡和 Git 分卷归档的后续成果以 [[Unpack/00-完整解包导航]] 的新版专题为准。生成资源应保留来源、哈希并注意商业素材的公开分发授权。

## 0. 准备

需要 Git、Python（Stage 0/1 Python 3.10+；Resource_Tool 的 Actions 实测环境为 Python 3.13）、7-Zip（`7z` 命令）及足够的本地磁盘空间。以下为 **PowerShell**，在仓库根目录运行。若已克隆，先拉取最新代码：

```powershell
git pull origin master
python -m unittest discover -s tests -v
```

需要使用外部资源工具时再初始化：

```powershell
git submodule sync --recursive
git submodule update --init --recursive
python scripts/tools/verify_tools.py
```

只有本地 Git 子模块 checkout 存在且对应依赖就绪，才可执行后续 Resource_Tool。具体资源工具用途见 [[工具与参考]]。

## 1. 还原原始 APK（88 个 7z 分卷）

**不要逐个解压**；从连续分卷的 `.001` 开始即可：

```powershell
$ExtractDir = "D:\PVZ2_Work\Original"
New-Item -ItemType Directory -Force $ExtractDir | Out-Null
7z x ".\ROMS\CHN\V4.2.8\PVZ2_4.2.8.7z.001" "-o$ExtractDir" -y
$Apk = (Get-ChildItem $ExtractDir -Recurse -Filter "*.apk" -File | Select-Object -First 1).FullName
if (-not $Apk) { throw "未找到 APK，请检查分卷/输出目录" }
(Get-FileHash $Apk -Algorithm SHA256).Hash
```

已实测源 APK SHA256：

```text
64b0f2cddb6221baf35fb32d4a0f6e64153428edf5ee5922beddb9726bedbda4
```

若哈希不一致，停止解包并检查 88 个分卷的完整性、顺序及源版本。该 APK 约 2.27 GB，Stage 1 RSB 总产物约 5.91 GB，另需 RSGP 和 Stage 3 产物及临时空间。

## 2. Stage 0：建立 APK 文件清单

```powershell
python scripts/audit/inspect_apk.py "$Apk" --out "audit/local/CHN-4.2.8" --full-crc
```

生成 `apk_audit.json`、`apk_filelist.csv`、`apk_headers.csv`。`--full-crc` 可选，表示对 ZIP 每个条目执行 CRC 校验；它不同于 APK 文件本身的 SHA256。

先检查清单的 RSLB、RTON、SMF 个数，以及路径大小是否与 [[versions/CHN/4.2.8]] 和 [[versions/CHN/4.2.8-parallel-unpack-results]] 对应。无法匹配就不要混用不同版本的脚本与资源。

## 3. Stage 1：RSLB → RSB、复制直接 RTON

### 3.1 先测 dino

```powershell
$Stage1 = "Unpack/CHN/4.2.8/stage1"
python scripts/unpack/parallel_unpack.py "$Apk" `
  --mode probe --out "$Stage1" --workers 2 `
  --sha256 64b0f2cddb6221baf35fb32d4a0f6e64153428edf5ee5922beddb9726bedbda4
```

此命令处理 `assets/dino.rsb.smf` 与 `assets/properties/resourcesDino.rton.smf`。验证 `report_probe.json`、`RSB/dino.rsb` 和 `RTON/resourcesDino.rton`，关注 `status`、`sha256`、`rsb` 组表字段。

### 3.2 再并发全量（可断点续跑）

```powershell
python scripts/unpack/parallel_unpack.py "$Apk" `
  --mode all --out "$Stage1" --workers 4 --resume `
  --sha256 64b0f2cddb6221baf35fb32d4a0f6e64153428edf5ee5922beddb9726bedbda4
```

`--workers` 支持 1～12；建议先用 4，根据内存和磁盘吞吐调整。`--resume` 对已有文件作有限的结构/长度检查以跳过；严格的**逐文件内容证明**仍建议独立保存并复核 SHA256。

正常目标：33 `.rsb`、18 直接 `.rton`、38 个原样 SMF，`report_all.json` 显示 89 项无失败。**此时还没有把 RSGP 内每个成员完整展开。**

串行备选命令：`python scripts/unpack/unpack_smf.py "$Apk" --mode probe --out "$Stage1"`；该实现报告名为 `extraction_report.json`，与并发版不同。

## 4. Stage 2：RSB → 2,964 个 RSGP 组

先对 dino 测试：

```powershell
python scripts/unpack/extract_rsg_groups.py "$Stage1/RSB" `
  --only dino.rsb --out "Unpack/CHN/4.2.8/stage2-dino" --workers 1
```

检查 `rsg_report.json` 的 `summary.groups=12` 且 `group_failure=0`，再运行全量：

```powershell
python scripts/unpack/extract_rsg_groups.py "$Stage1/RSB" `
  --out "Unpack/CHN/4.2.8/stage2" --workers 4 --resume
```

每个 RSB 建独立目录，按序号保存 `00000.rsg` 等。报告记录组名、在原 RSB 中的偏移、长度和 SHA256；组魔数是 `pgsr`。这一命令**只导出资源组，不拆其内部文件**。对本版本的真实实测为 2,964/2,964。

## 5. Stage 3：RSGP 内部文件和可解析 RTON → JSON

该阶段使用固定版本的 [CN Resource_Tool](https://github.com/lei1737524550/PVZ2-Chinese-Version-Reverse-Tools)，仓库内子模块路径为 `tools/PVZ2-CN-Reverse-Tools`。2026-11-06 实测的上游 commit 为 `04f57f42080ef831545c9b2877f81f811f0be4e2`。

```powershell
$Tool = "tools/PVZ2-CN-Reverse-Tools/Resource_Tool/main.py"
python "$Tool" -unpack "$Stage1/RSB" -json `
  -o "Unpack/CHN/4.2.8/stage3" -j 4
python scripts/audit/report_secondary.py "Unpack/CHN/4.2.8/stage3" `
  --out "audit/local/CHN-4.2.8/secondary-report.json"
```

**为什么这里输入 RSB，而不是 Stage 2 的 `.rsg`？** 现有 CN Resource_Tool 支持从完整 RSB 直接编排资源组及内部成员提取；Stage 2 的独立 RSGP 抽取用于保留证据与校验，两条路径可以对照。无需把已经切出的 RSGP 再手动塞回 RSB。

2026-11-06 Actions 实测的全量输出：14,869 个内部文件；8,091 个 RTON 对应 JSON 语法校验成功；剩余 6,778 个仍是原格式。最终可转换输出位于上游工具生成的 `*_JSON` 目录，细节以运行日志为准。**本地复现不保证所有文件无误，仍应对比报告。**

## 6. 另一条支线：18 个顶层直接 RTON → JSON

```powershell
python "$Tool" -unpack "$Stage1/RTON" -json `
  -o "Unpack/CHN/4.2.8/direct-rton" -j 4
python scripts/audit/report_secondary.py "Unpack/CHN/4.2.8/direct-rton" `
  --out "audit/local/CHN-4.2.8/direct-rton-report.json"
```

此路径输入的是 Stage 1 复制得到的 18 个顶层 `*.rton`，不应再算进 RSB 内部的 8,091 个 JSON。对应实测任务 18/18 成功。

## 8. GitHub Actions 执行与下载

无需本地一次生成所有数据时，可在仓库 **Actions** 中手动触发：
1. `unpack-chn-4.2.8.yml`：源 APK 校验、Stage 1、8 个 RSB shards。
2. `unpack-chn-4.2.8-rsg.yml`：下载 Stage 1 的 RSB shards，切出 RSGP。
3. `unpack-chn-4.2.8-internal.yml`：下载 Stage 1 的 RSB shards，独立解析内部成员/JSON。
4. `unpack-chn-4.2.8-direct-rton.yml`：获取 Stage 1 的 18 个直接 RTON 转 JSON。

详情及原始成功运行号见 [[工作流与Artifacts]]。**Artifacts 保留 3 天**（以工作流配置为准），过期需要重新执行。重新跑 Stage 1 后，Stage 2/3 的 `source_run` 应指向新的成功运行号；direct-rton 工作流当前使用硬编码 Stage 1 run ID，不能误认为自动追踪最新结果。

## 9. 失败排查与结果验收

- **7z 解包失败**：确认从 `.001` 开始、88 个分卷齐全、磁盘空间与 APK SHA。
- **RSLB 块错误**：对照 `RSLB v1` 描述符/块链接与解压长度，记录原路径和块序号，切勿忽略失败。
- **RSB/RSGP magic 错误**：检查 `1bsr` / `pgsr`、偏移与声明长度；不能将“文件存在”当作解析成功。
- **Resource_Tool 未找到**：执行 `git submodule update --init --recursive`，核对固定 SHA，确认 Python 环境。
- **JSON 校验错误**：以 `report_secondary.py` 的错误路径为准；大于 64 MiB 的 JSON 当前脚本会单列为 unchecked-large，不属于已校验有效项。
- **Artifacts 不存在**：先检查源运行号、成功状态及保留期限，必要时重跑上游工作流。

每一次复现实验最少保存：`source_apk_sha256`、工具 commit、命令、实际输入路径、各层 success/failed/unsupported/skipped 总数，以及逐文件错误/输出哈希。参考 [[研究证据规范]] 与 [[versions/CHN/4.2.8-parallel-unpack-results]]。

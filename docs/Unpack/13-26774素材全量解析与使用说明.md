## 环境准备：WSL/Linux（Windows 也可以使用）

确保安装 Python 3.10 以上、tar、zstd；Pillow 用于实际 PNG 像素解码（可选）：

~~~bash
sudo apt update
sudo apt install -y zstd tar python3
python3 -m pip install Pillow

git pull origin master
python3 -m compileall -q scripts/parse
python3 -m unittest discover -s tests -p 'test_asset_formats.py' -v
python3 -m unittest discover -s tests -p 'test_parse_shard.py' -v
~~~

如果 Pillow 不存在，PNG 只能检查 IHDR 尺寸，状态为 png-structural；安装后可尝试真正解码像素，状态为 png-decoded。Windows PowerShell 输入 wsl，再切到仓库所在盘对应的 /mnt/... 路径。

## 最简单的一键本地全量执行

在已完整检出 15 个 Git 分片的 WSL/Linux 仓库根目录执行：

~~~bash
python3 scripts/parse/parse_all.py \
  --workers 2 \
  --max-refs-per-json 24 \
  --resume
~~~

脚本每次只将一个分片解压到临时目录，校验并解析后删除临时解包文件。当前已完成的 shard 结果会由 --resume 检查来源哈希和计数后复用。默认输出目录为 audit/local/CHN-4.2.8/deep-parse/：shards/ 下是各分片检查点；merged/ 下是最终 SQLite、CSV 和 SUMMARY.json。Media-06 会明确标为 MISSING。如果添加 --require-all，遇到缺失的 Media-06 会主动报错，不会生成“全部完整”的假结论。

对于存储紧张的 WSL 环境，可指定 --tempdir /mnt/x/你的临时目录，将大文件的短期恢复位置放在另一个有空间的卷。该路径需事先存在。

## 本地单分片操作示例

以真实 Media-00 的 1,366 个文件为例，从已提交 Git 原始压缩分卷恢复：

~~~bash
python3 scripts/archive/restore_git_shard.py \
  Unpack/CHN/V4.2.8/Media/shard-00 \
  --out audit/local/restored-media-00

python3 scripts/parse/parse_shard.py \
  --root audit/local/restored-media-00 \
  --catalog Catalog/CHN/V4.2.8/shards/Media-00/files.csv \
  --out audit/local/parsed-media-00 \
  --workers 2 --max-refs-per-json 24
~~~

输入换成 Internal/shard-05 及对应的 Internal-05/files.csv，可研究植物、僵尸、LevelDefinition 和 WaveManager 数据。

单分片输出：
- files.csv：原路径、格式、大小、SHA256、解析状态及 metadata_json；
- classes.csv：每个源 JSON 中的 objclass 类别及记录数；
- references.csv：真实 RTID 文本、alias、命名空间、JSON 对象序号和字段路径；
- SUMMARY.json：各格式数量、处理等级、RTID 全量发现数与样本截断数、异常计数。

默认每个 JSON 最多保存 24 条 RTID **样本**，但 SUMMARY 中会统计实际发现的总条数。如需详细调查可使用 --max-refs-per-json 200，注意输出文件会明显增大。关卡深度完整外键关系另见 [[Unpack/05-关卡与波次RTID]]。

## 解析状态的准确解释

| parser_status | 本次能证明 | 本次不能证明 |
|---|---|---|
| parsed-json | JSON 语法、对象类与部分 RTID | 游戏运行逻辑 |
| png-decoded / png-structural | 已读取 PNG 像素 / 仅检查 PNG IHDR | 图集切片及动画正确播放 |
| riff-structural | WEM 的 RIFF/fmt 元信息 | 音频 WAV 已解码 |
| riff-partial | 非标准 RIFF 存在 chunk 长度歧义，保留源偏移、长度 | 不能直接判断文件损坏 |
| bnk-chunks-parsed | BNK 分块及 DIDX/DATA 边界和媒体记录数 | Wwise 事件已正常播放 |
| lua-bytecode-header | Lua 字节码版本字段 | Lua 已反编译且能执行 |
| text-structure / sfnt-directory | 纯文本/XML/INI 和字体目录 | 游戏语义或字体公开授权 |
| opaque-preserved | 原始 PTX/PAM/POPFX 等源字节可信 | 已经转换或可渲染 |
| unresolved / parse-error | 保留不理解的结构或解析异常信息 | SHA256 不通过（完整性另判） |

此前 Media-00 真实试验的 39 个特殊 WEM 不应凭通用 RIFF 规则直接认定为损坏，已增加 riff-partial 的证据记录。

还可以使用下面的 SQL 搜索：

~~~sql
SELECT format,parser_status,count(*) FROM assets

SELECT stage,shard,original_path,parser_status
FROM assets WHERE lower(original_path) LIKE '%peashooter%' LIMIT 100;

SELECT objclass,sum(object_count) AS total FROM object_classes
GROUP BY objclass ORDER BY total DESC LIMIT 50;

SELECT stage,shard,original_path,rtid FROM rtid_samples
WHERE namespace='CurrentLevel' LIMIT 50;

SELECT stage,shard,total_files,parse_errors,unresolved FROM stages;
~~~

### 剩余真实异常的研究方向

- 非 BKHD：原始 Internal-01 的 ZOMBIE_WILDWEST_PONCHO_ZOMBIE.BNK 和 Media-01 派生副本的起始字节都为 78 da d4 b7。**可能需要单独检查压缩或包装，不能凭头部猜测编码或将它计为 Wwise BNK 已解码。**
- 特殊 BNK：Internal-03 的 PLANT_SNAPPEA.BNK 有未解释的尾部，现有脚本保留偏移及尾部十六进制片段。
- XML：Internal-05 的 dynamic/LawnStrings/PROPERTIES/DEFAULT.XML 存在解析器不认识的实体引用，不会擅自补写缺失 DTD。
- WEM：245 条文件的 RIFF/数据块声明比当前存储的字节多，可能涉及流式或预取；需要查原 BNK 的完整字节/分配及游戏运行时，而不是简单将它们认定为损坏。

### 用 SQLite 单独查特殊音频

~~~sql
SELECT stage,shard,original_path,parser_status,
       json_extract(metadata_json,'$.declared_total_bytes') AS declared_bytes,
       json_extract(metadata_json,'$.actual_bytes') AS stored_bytes
FROM assets WHERE parser_status='riff-partial'
ORDER BY declared_bytes DESC LIMIT 30;

SELECT original_path,metadata_json FROM assets
WHERE parser_status IN ('bnk-partial','xml-partial','unresolved')
ORDER BY original_path;
~~~
